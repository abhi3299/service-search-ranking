# service-search-ranking

A search engine for a home-services marketplace: **1,532 services across seven
verticals**, retrieved by meaning as well as words, and ordered by a sort you
can read.

> **The data here is synthetic.** Every service, price, treatment line, order
> count and shopper history in this repository is generated by
> `pipeline/1_generate_catalogue.py`. No real customer, catalogue or commercial
> data is present. The *shape* is modelled on a production catalogue, because
> that shape is what makes the problem hard.

### ▶ [Open the live demo](https://abhi3299.github.io/service-search-ranking/)

It runs entirely in the browser — nothing to install, no server, no terminal.
Type a query, switch personas in the header, watch the ordering change.

## The problem

Keyword search over a service catalogue fails in three specific ways, and each
one costs orders.

**It matches words, not meaning.** A customer's words rarely equal the
catalogue's words. *"hair removal"* should return waxing. *"facial for glow"*
should return brightening facials. Keyword matching misses these unless
somebody tagged every synonym by hand, and lexical matching is binary — a
near-miss and a total miss rank identically.

**Everyone sees the same list.** Ordering by static popularity means a
first-time visitor and a customer who has booked the same treatment ten times
get identical results. The single most reliable signal about a returning
customer — what she has already paid for — goes unused at the exact moment she
is choosing.

**The catalogue's own shape works against it.** In this dataset the Waxing hall
alone holds **258 services under 93 distinct names**, and the top of that list
is near-identical combinations differing only by treatment line. A shopper
scrolling it is not choosing, she is disambiguating. The same service also
exists on several floors with different ids, so printed naively it reads as a
bug.

## The design

Eight stages, fixed order. Each either narrows what is eligible or decides an
order within it. **Nothing is scored and nothing is weighted**, so any two
results can be explained by naming the one question that separated them.

| Stage | What it decides |
|---|---|
| 0 · Suggestions | Five queries that each return something, before she finishes typing |
| 1 · Spelling | Repairs words that exist nowhere in the catalogue |
| 2 · The lift | Which hall the query names, if any — 1,532 services down to one hall |
| 3 · Retrieval | Lexical and vector, run in parallel and fused by rank |
| 4 · Bands | How well each result answers the query, in five tiers |
| 5 · Scope | How much of a result is about something she did not ask for |
| 6 · The sort | Seven questions asked in sequence |
| 7 · Presentation | Filter rows, one row per service, and range cards |

### The three sorts

Ranking balances three things, and the order they are asked in is the whole
design.

**Relevance first.** Which band a result falls in, then how much of it the
shopper did not ask for. Both are questions about the query, not about her.

**Then her history.** How many times she has booked this exact service, then
whether it is her usual treatment line. A line needs **two** purchases before it
counts — one is a trial, not a habit — and a variant needs to clear a demand
floor before her preference can promote it, so a single curious purchase cannot
reorder the catalogue for her forever.

**Then demand.** Order volume, bucketed into tiers so that small differences do
not decide anything, with the exact count only as a final tie-break.

Demand is asked **fifth and seventh**. It can only ever separate results that
already tied on relevance and on her history, so the business cannot push a
result above a better match. That is structural rather than a rule somebody has
to remember.

### Why bands, and not a weighted score

A weighted score is a single number with no memory of how it was reached. Two
results can tie for opposite reasons and nobody can say why one won; tuning one
weight silently moves everything else; and "relevance is a floor" becomes a
hope rather than a property.

A cascade is explainable by construction. The five bands are:

| Band | Meaning |
|---|---|
| 1 | Every distinguishing word, as the phrase she typed |
| 2 | Every distinguishing word, scattered |
| 3 | Some of the distinguishing words |
| 4 | Only family words — the category word, not the distinguishing one |
| 5 | Found by meaning, with no word in common |

Because the band is the first key, **a result found only by the vector half can
never outrank one that matched the words she actually typed**. That guarantee
survives every later stage, including the filters, because filters are applied
*after* the sort — a filtered list is always a subsequence of the unfiltered
one.

It also makes the behaviour testable. "Every *Full Legs* service outranks every
*Half Legs* service for the query *full legs waxing*" is a property you can
assert. Against a weighted score it is not.

The tests lift the engine out of the shipped HTML with a regular expression and
run it in a function scope, so **a test cannot pass against code that is not in
the artifact**.

## Running it

No build step, no server, no dependencies.

```bash
python3 pipeline/1_generate_catalogue.py   # invent the catalogue
python3 pipeline/2_build_canonical.py      # collapse duplicates, build vectors
python3 pipeline/5_build.py                # embed data into the prototypes

node tests/test_search.js                  # 107 core ranking checks
node tests/test_search_v9.js               #  44 variant clustering
node tests/test_search_v10_1.js            #  73 spelling
node tests/test_search_v11.js              # 132 ranges, type-ahead, personalisation

SEARCH_HTML=prototype/search_v11.html node tests/test_search.js
#   the core suite re-run against v11 — proves the ranking underneath did not move
```

Then open `prototype/search_v11.html`. Switch the shopper selector to see
personalisation change the results, the range cards and the suggestions.

| `search_v9.html` | One row per service — variant clustering |

## What is real and what is a stand-in

| Component | Status |
|---|---|
| Retrieval, bands, scope, the sort, filters, ranges | Production-shaped |
| Catalogue, orders, aliases, suggestions | **Synthetic**, generated here |
| Vector half | **Stand-in** — TF-IDF + random projection, where a learned embedding belongs |
| Shopper histories | **Synthetic** — four fixed profiles |

The vector half is the one component that would be replaced before any real
deployment. The architecture around it is final: two retrievers fused by rank,
with the weaker half floored into the lowest band so it can never outrank a
word match.

## Repository

```
pipeline/   1_generate_catalogue.py   invent the catalogue
            2_build_canonical.py      collapse duplicates, vectors, suggestions, personas
            5_build.py                embed the data into each prototype
            6_leak_check.py           fail the build if anything non-synthetic appears
data/       catalogue.json  orders.json  personas.json
prototype/  five versions, source template and built file for each
tests/      four suites, 356 checks
```

Edit `*.template.html`, never the built `*.html` — the latter is generated and
overwritten on every build.

## On the synthetic boundary

This project was ported from a private one, and the data layer was rebuilt from
scratch rather than anonymised. `pipeline/6_leak_check.py` enforces that: it
scans every file for terms that belong to the original catalogue, and verifies
that the data declares itself synthetic and that every built page carries a
visible notice. It runs before each commit.

It is in the repository because the first port leaked in four separate ways —
two migration scripts still carried a mapping table of the original names, some
hard-coded vocabularies kept their original entries, test fixtures named real
services, and one substitution replaced a term with a longer string that still
contained it. Catching that by eye is not a strategy.
